# PRD: CareerPilot 商用化一期（P0）

| 项目 | 内容 |
|---|---|
| 文档类型 | Product Requirements Document（需求拆分稿） |
| 来源 | `requirement.md`（CareerPilot 商用化就绪分析报告） |
| 范围 | 商用化一期 P0：可安全对客的 ToC + ToB 双通道底座 |
| 文档状态 | 待业务确认；不得据此直接跳过开放问题开始上线 |
| 输出目的 | 供开发者或 AI agent 按依赖顺序逐个实现、验证和交付 |

> 本 PRD 只拆分需求，不实施功能。支付、完整运营报表、品牌重构等 P1/P2 内容明确列入 Non-Goals，避免一期范围失控。

## 1. Introduction

CareerPilot 已具备简历编辑、AI 优化、导出分享、职业照和模拟面试等用户端能力，但当前默认使用浏览器指纹身份、SQLite 和用户自备 AI Key（BYOK），缺少角色、机构、点数/额度、管理后台和完整的商用安全边界。

商用化一期要在保留现有业务能力的前提下，建立一套可安全对客的双通道底座：

- ToC 用户通过正式身份注册登录，使用个人点数调用平台托管 AI。
- ToB 用户归属机构并使用机构额度；机构管理员仅管理本机构成员和用量。
- 超级管理员管理用户、机构、点数/额度、AI 供应商密钥、模型目录和扣点规则。
- 所有 AI 调用只使用服务端托管密钥，并经过认证、归属校验、模型授权、限流、额度预占、调用和结算。
- 生产环境使用 PostgreSQL、正式认证、最小备份恢复和基本合规能力。

## 2. Goals

- 100% 关闭生产环境的指纹身份和 SQLite 默认降级，所有不安全配置均 fail-closed。
- 建立平台角色、机构成员、个人点数账户、机构额度账户和不可变流水。
- 让 ToC 用户完成“注册 -> 获得点数 -> 调用 AI -> 扣点 -> 查看流水”的真实闭环。
- 让 ToB 用户完成“机构开户 -> 管理员授权 -> 成员加入 -> 调用 AI -> 扣机构额度”的真实闭环。
- 终端用户页面、请求、浏览器存储和响应中均不再出现平台或用户 AI Key。
- 所有私有 API 都具备登录态、角色、租户和资源所有权校验；被拒绝的请求不调用供应商、不扣点、不改变数据。
- 超级管理员可完成一期所需的用户、调账、机构、供应商、模型和规则管理。
- 用户可导出个人数据、注销账号，并能访问真实的隐私政策和服务条款页面。
- 关键认证、越权、跨租户、并发扣点、幂等、限流和失败补偿场景进入自动化回归门禁。

## 3. Default Assumptions

以下是假设，不是已确认的长期商业策略；若业务方调整，必须先更新本 PRD 中受影响的 stories 和验收标准。

1. **一期双通道同期具备。** ToC 与 ToB 均纳入 P0，但不接支付。
2. **ToC 一期只支持注册赠点和超管手工调账。** 充值、退款和支付对账进入 P1。
3. **ToB 一期采用“机构席位上限 + 手工分配机构额度”。** 年费、按席位计费或机构点数包属于销售策略，不在 P0 实现。
4. **认证默认方案为邮箱验证码（无密码）+ 保留现有 Google OAuth。** 若业务确认一期仅使用 OAuth，可删除邮箱验证码分支；生产环境始终禁止指纹认证。
5. **机构管理员一期通过精确邮箱添加已注册用户。** 邮件邀请、批量导入和 SSO 进入后续阶段。
6. **普通用户一期最多只有一个有效计费归属。** 无机构时使用个人点数；加入有效机构后使用该机构额度。多机构切换需另行设计，系统不得静默选择第一条 membership。
7. **AI 计费采用“调用前预占，结束后结算或释放”。** 支持固定单次点数和按实际 Token 结算；具体价格由超管配置并在流水中保存快照。
8. **机构管理员默认无权查看成员的简历、面试内容或完整 Prompt。** 其权限只包括成员、席位、额度和聚合用量。
9. **账号注销采用重新认证 + 明确二次确认。** 业务数据删除，必须保留的账务/安全记录按法务确认后的规则匿名化。

## 5. User Stories

### US-001: 商用运行配置 fail-closed

**描述：** 作为平台运维人员，我希望生产环境在认证、数据库、密钥或迁移配置不安全时拒绝启动，以免系统在匿名、单机数据库或半迁移状态下对客服务。

**优先级：** P0  
**依赖：** 无

**Acceptance Criteria：**

- [ ] `NODE_ENV=production` 且指纹认证仍启用时，应用在接受流量前以非零状态失败，并指出不安全配置项。
- [ ] 生产环境配置为 SQLite、缺少 PostgreSQL 连接、使用占位 `AUTH_SECRET`、缺少独立的 AI 凭据加密主密钥时，应用均拒绝启动。
- [ ] 数据库迁移失败时 readiness 保持失败，进程不得仅记录错误后继续提供业务 API。
- [ ] 生产空库初始化不会自动创建指纹用户、演示用户或示例简历。
- [ ] 本地开发可在显式开发开关下继续使用 SQLite/测试身份，但该开关在生产配置中无效。
- [ ] 自动化配置矩阵覆盖上述成功与失败路径，断言失败场景没有监听业务端口。
- [ ] `pnpm type-check`、`pnpm lint` 和相关配置测试通过。

### US-002: PostgreSQL 单一商用 Schema 与迁移基线

**描述：** 作为平台运维人员，我希望商用数据结构以 PostgreSQL 为唯一生产基线，以便新部署、存量升级和故障恢复得到一致结果。

**优先级：** P0  
**依赖：** US-001

**Acceptance Criteria：**

- [ ] 一套明确的生产 schema 定义覆盖用户、认证账号、简历、分享、AI 会话、面试以及本 PRD 新增的商用实体。
- [ ] 全新 PostgreSQL 数据库可从零执行全部迁移并成功启动应用。
- [ ] 使用包含用户、简历、分享、AI 会话和面试记录的代表性旧数据执行升级后，记录数量、归属和可读取内容保持一致。
- [ ] PostgreSQL 中的外键、级联规则、唯一约束、余额非负约束和常用归属索引可通过数据库查询或失败写入用例验证。
- [ ] 重启应用不会重复执行破坏性 seed，也不会产生重复角色、账户、赠点或 membership。
- [ ] 升级前备份点和失败回退步骤有可执行记录；至少完成一次测试环境回退演练。
- [ ] SQLite 如继续用于本地开发，不得再作为生产 schema 的隐式来源；生产迁移与运行时语义一致。
- [ ] `pnpm type-check`、`pnpm lint`、迁移测试和数据回归测试通过。

### US-003: 正式注册、登录与 Session 生命周期

**描述：** 作为新用户，我希望通过正式身份完成注册和登录，以便安全地持续访问自己的数据，而不是依赖可伪造的浏览器指纹。

**优先级：** P0  
**依赖：** US-001、US-002

**Acceptance Criteria：**

- [ ] 使用一个全新唯一邮箱获取验证码并完成首次登录后，只创建一个用户身份和一个对应认证账号。
- [ ] 验证码具有有效期和单次使用约束；错误、过期和已使用验证码均返回明确且不泄露账号存在性的错误。
- [ ] 使用同一邮箱再次登录或通过已绑定的 Google OAuth 登录，不会重复创建用户或赠点。
- [ ] 登录成功后使用 `HttpOnly`、生产环境 `Secure` 且具备合理 `SameSite` 策略的 session cookie；认证 token 不写入 `localStorage`。
- [ ] 访问带 `callbackUrl` 的受保护页面时，登录成功后返回原目标；刷新页面仍保持登录。
- [ ] 主动退出后原 session 失效，再访问受保护 API 返回 `401`。
- [ ] 生产环境伪造 `x-fingerprint` 请求头不能创建身份、恢复身份或访问任何私有资源。
- [ ] 注册、登录、验证码重放、OAuth 合并、刷新和退出均有自动化测试。
- [ ] `pnpm type-check`、`pnpm lint` 和相关认证测试通过。

### US-004: 平台角色、账号状态与超级管理员 Bootstrap

**描述：** 作为平台负责人，我希望明确区分超级管理员和普通平台用户，并可冻结异常账号，以便所有管理和风控操作都有可信的服务端授权依据。

**优先级：** P0  
**依赖：** US-002、US-003

**Acceptance Criteria：**

- [ ] 平台级角色至少包含 `super_admin` 与 `user`；账号状态至少包含 `active` 与 `suspended`。
- [ ] 超级管理员只能通过显式、可审计的部署 bootstrap 方式创建或授予；“首个注册用户自动成为超管”不被允许。
- [ ] session 可提供角色信息用于界面展示，但每次敏感服务端操作仍校验当前数据库角色和账号状态。
- [ ] 账号被冻结后，下一次私有 API 请求即返回稳定的 `ACCOUNT_SUSPENDED` 错误，且不改变数据、不调用 AI 供应商、不产生消费流水。
- [ ] 解冻后用户可重新建立有效 session；角色或状态变更不会依赖旧客户端缓存长期生效。
- [ ] 普通用户无法通过请求体、cookie、请求头或用户资料更新接口提升自己的角色或状态。
- [ ] 授权、冻结、解冻和 bootstrap 操作产生不含敏感凭据的审计记录。
- [ ] `pnpm type-check`、`pnpm lint` 和角色/状态测试通过。

### US-005: 机构与 Membership 租户模型

**描述：** 作为平台运营人员，我希望用户通过机构 membership 获得机构角色，而不是使用单一全局角色，以便 ToC 与多个 ToB 租户保持清晰的数据边界。

**优先级：** P0  
**依赖：** US-002、US-004

**Acceptance Criteria：**

- [ ] 机构至少包含唯一标识、名称、状态、席位上限、创建者和时间字段。
- [ ] Membership 至少区分 `org_admin` 与 `member`，并记录有效/移除状态；机构角色不存成全局 `users.role=org_admin`。
- [ ] ToC 用户可以没有机构 membership，并继续使用个人账户。
- [ ] 同一用户不能在同一机构中产生重复有效 membership；超过席位上限时新增成员被原子拒绝。
- [ ] 一期若检测到普通用户拥有多个有效计费机构，不得静默选择其中一个；请求返回可识别的计费归属错误。
- [ ] 停用机构或移除成员后，该用户下一次机构范围请求和机构额度消费均被拒绝。
- [ ] 机构管理员默认无法读取成员的简历、面试记录、聊天正文或完整 Prompt。
- [ ] 跨机构查询、写入和统计请求返回 `404` 或稳定的无权限响应，且不泄露目标是否存在。
- [ ] `pnpm type-check`、`pnpm lint` 和租户隔离测试通过。

### US-006: 个人点数与机构额度不可变账本

**描述：** 作为平台财务与运营人员，我希望个人点数和机构额度通过可审计、幂等且不能透支的流水变化，以便每笔 AI 消费和人工调账都可核对。

**优先级：** P0  
**依赖：** US-002、US-005

**Acceptance Criteria：**

- [ ] 每个 ToC 用户拥有独立个人账户；每个 ToB 机构拥有独立机构额度账户，两类账户不能串账。
- [ ] 余额只能通过追加流水改变；已入账流水不能被普通更新或删除。
- [ ] 每条流水包含账户、变动前余额、变动值、变动后余额、原因、操作者、业务关联 ID、幂等键、时间和价格规则快照。
- [ ] 注册赠点对同一用户最多入账一次；重复回调或重试不会重复赠点。
- [ ] 同一幂等键的重复请求返回首次结果，不新增流水、不重复扣减。
- [ ] 多个并发预占或扣减无法使余额小于零；失败事务不留下半条流水或错误余额。
- [ ] 个人消费只影响个人账户，机构成员消费只影响当前有效机构账户。
- [ ] 余额可从完整流水重新核对，核对结果与账户快照一致。
- [ ] `pnpm type-check`、`pnpm lint`、账本幂等和并发测试通过。

### US-007: 托管供应商凭据与模型目录数据底座

**描述：** 作为超级管理员，我希望集中维护 AI 供应商、加密凭据、模型能力和扣点规则，以便终端用户只选择获授权模型而不接触密钥。

**优先级：** P0  
**依赖：** US-001、US-002、US-004

**Acceptance Criteria：**

- [ ] 供应商记录至少支持类型、受控服务地址、启用状态、凭据版本和最后验证结果。
- [ ] 模型目录至少支持供应商、模型标识、显示名称、能力类型（文本/生图）、档位、启用状态、用户可见范围和计价方式。
- [ ] 计价规则支持固定单次点数，以及按输入/输出 Token 结算所需的独立费率和最大预占值。
- [ ] 供应商密钥使用独立于 `AUTH_SECRET` 的主密钥或外部 Secret/KMS 加密；数据库查询不能直接得到可用明文 Key。
- [ ] 所有普通和管理读取接口只返回掩码及凭据元数据，不返回完整密钥。
- [ ] 应用日志、审计记录、错误响应和客户端埋点均不包含完整 Key、Authorization 头或解密后的凭据。
- [ ] 生产缺少凭据解密条件时，配置检查失败；不得降级为读取客户端 Key。
- [ ] 模型或供应商被停用后，新调用在到达供应商前被拒绝。
- [ ] `pnpm type-check`、`pnpm lint`、加密往返和密钥泄漏测试通过。

### US-008: 最小安全与运营审计事件

**描述：** 作为平台安全负责人，我希望关键管理和权限变化留下不可抵赖的审计事件，以便追查调账、授权、冻结和密钥轮换。

**优先级：** P0  
**依赖：** US-004、US-005、US-006、US-007

**Acceptance Criteria：**

- [ ] 冻结/解冻用户、调整点数/额度、创建/停用机构、任命/回收管理员、修改模型规则、轮换供应商凭据均产生审计事件。
- [ ] 每条事件包含操作者、动作、目标类型与 ID、租户范围、时间、请求关联 ID 和经过脱敏的变更摘要。
- [ ] 凭据变更事件只记录版本或掩码，不记录明文 Key；用户简历、面试正文和完整 Prompt 不进入普通审计事件。
- [ ] 审计事件不能由普通用户或机构管理员修改/删除；机构管理员只能读取明确开放的本机构事件。
- [ ] 同一幂等管理请求不会产生重复业务变更或重复审计事件。
- [ ] 未成功的敏感操作记录失败结果，但不得把无权限目标的敏感信息写入响应。
- [ ] `pnpm type-check`、`pnpm lint` 和审计覆盖测试通过。

### US-009: 统一认证、RBAC、租户与计费上下文守卫

**描述：** 作为平台开发者，我希望所有私有 API 使用一致的服务端访问上下文，以便认证、角色、机构和计费账户不会在各路由中以不同方式判断。

**优先级：** P0  
**依赖：** US-003、US-004、US-005、US-006

**Acceptance Criteria：**

- [ ] 建立明确的公共路由白名单；除认证回调、法律页面、公开分享和健康检查外，API 默认要求登录。
- [ ] 未登录访问任一私有 API 返回 `401 AUTH_REQUIRED`，不会创建指纹用户或业务数据。
- [ ] 普通用户访问超管 API 返回 `403 FORBIDDEN`；非本机构管理员访问机构管理 API 返回无泄漏的 `403/404`。
- [ ] 所有上下文都从服务端可信 session 和数据库解析 actor、平台角色、账号状态、机构 membership 与计费账户，不信任客户端声明的 user/role/org/balance。
- [ ] 冻结账号、停用机构、移除 membership 或计费归属不明确时，在业务写入和供应商调用前拒绝请求。
- [ ] 公开分享路由只能读取明确公开的数据，不能借分享 token 获得所有者身份或其他私有资源。
- [ ] 自动化访问矩阵覆盖匿名、普通用户、机构成员、机构管理员、超级管理员和冻结账号。
- [ ] `pnpm type-check`、`pnpm lint` 和访问矩阵测试通过。

### US-010: 修复现有资源所有权与嵌套资源越权

**描述：** 作为用户，我希望其他已登录用户也不能通过猜测 ID 读取或修改我的简历、AI 会话和面试资源，以便平台托管密钥上线后不会放大现有越权风险。

**优先级：** P0  
**依赖：** US-009；必须早于 US-014

**Acceptance Criteria：**

- [ ] AI Chat 使用 `resumeId` 前验证简历属于当前用户；AI tools 只能修改同一已验证简历。
- [ ] AI Chat 写入 `sessionId` 前验证会话属于该简历和当前用户。
- [ ] Chat session 的列表、创建、详情、分页消息和删除均通过简历反查当前用户所有权。

### US-034: 安全、成本与发布回归门禁

**描述：** 作为发布负责人，我希望高风险负向场景在每次发布前自动验证，以便一期不会因后续改动重新出现越权、开放代理或重复扣点。

**优先级：** P0

**Acceptance Criteria：**

## 6. Functional Requirements

- **FR-001:** 生产环境必须禁用指纹身份和 SQLite，并在不安全配置或迁移失败时拒绝服务。
- **FR-002:** PostgreSQL 必须是商用数据结构与迁移的唯一生产基线，并具备外键、唯一约束、级联和归属索引。
- **FR-003:** 系统必须至少支持一种经批准的正式自助注册方式，并使用服务端 session；不得把认证 token 存入浏览器本地存储。
- **FR-004:** 系统必须区分平台 `super_admin/user` 与机构 membership `org_admin/member`，并支持账号和机构停用状态。
- **FR-005:** 超级管理员必须通过显式 bootstrap 创建；任何用户不得自助提权。
- **FR-006:** ToC 用户必须拥有个人点数账户，ToB 机构必须拥有独立机构额度账户，两者不得串账或自动回退。
- **FR-007:** 所有余额变化必须通过不可变、幂等、可审计流水完成，且任何并发路径均不得产生负余额。
- **FR-008:** 系统必须支持注册赠点、个人/机构人工调账、必填备注、规则快照和每日上限。
- **FR-009:** 平台 AI 凭据必须仅由超管维护并加密保存，普通读取、响应和日志不得返回明文。
- **FR-010:** 模型目录必须定义能力、供应商、启用状态、授权范围、输入/输出限制和固定/Token 计价规则。
- **FR-011:** 除明确公共白名单外，API 必须默认要求登录，并在服务端验证角色、状态、租户和资源所有权。
- **FR-012:** 私有嵌套资源必须同时验证父资源和子资源归属；跨用户/机构请求不得产生数据、供应商或账本副作用。
- **FR-013:** 高成本入口必须按 IP、用户、计费账户和能力限流，并限制文件、图片、Prompt、消息和模型 steps。
- **FR-014:** 服务端不得根据终端用户输入访问任意 Provider/Base URL；允许的自定义上游必须经过严格出站校验。
- **FR-015:** 所有 AI 调用必须通过统一 Gateway，并执行认证、归属、模型授权、限流、预占、调用和结算/释放。
- **FR-016:** 每个业务 AI operation 和真实供应商 attempt 必须可追踪，支持嵌套调用、重试、流式和部分成功计量。
- **FR-017:** 客户端提交的 AI Key、Provider 或 Base URL 不得影响生产调用；遗留本地 Key 必须从浏览器清除。
- **FR-018:** 终端用户只能看到并选择当前账号获授权且已启用的模型。
- **FR-019:** 余额不足、机构额度不足、限流、模型停用、账号冻结和供应商失败必须返回不同、稳定且可本地化的错误。
- **FR-020:** 超管必须能管理用户冻结、点数调账、注册规则、机构开户、管理员授权、供应商、模型和扣点规则。
- **FR-021:** 机构管理员只能管理本机构成员、席位和查看最小用量，不得查看平台 Key、其他机构或成员业务正文。
- **FR-022:** 用户必须能够读取自己的余额/额度摘要和分页流水，不能通过 ID 参数读取其他账户。
- **FR-023:** 用户必须能够导出完整个人数据，并在重新认证与二次确认后注销账号、撤销 session 和公开分享。
- **FR-024:** 隐私政策和服务条款必须提供真实中英文公共页面，并记录用户同意的版本和时间。
- **FR-025:** 关键管理、权限、调账和凭据变更必须生成脱敏、不可修改的最小审计事件。
- **FR-026:** 生产必须具备加密 PostgreSQL 备份、隔离恢复演练和不泄密的 readiness 检查。
- **FR-027:** 所有新增用户界面和错误文案必须同时支持 `zh` 与 `en`，且移动端和桌面端均无文字溢出或不可操作控件。
- **FR-028:** 发布门禁必须覆盖认证、IDOR、租户隔离、SSRF、限流、并发扣点、幂等、失败补偿和敏感信息泄漏。

## 9. Technical Considerations

- **数据库：** 当前 SQLite 与 PostgreSQL schema 已出现语义差异；P0 应建立单一生产 schema 和可重复迁移路径，而不是继续手工镜像两份定义。
- **认证：** 当前 NextAuth 版本为 beta。立项时必须决定继续并锁定经验证版本，或先升级到稳定方案；不得在同一 story 中同时重写业务认证和所有商业模块。
- **角色模型：** `super_admin` 是平台角色，`org_admin/member` 属于 organization membership。不要用一个全局 role 字段表达全部关系。
- **服务上下文：** 私有服务统一解析 actor、平台角色、账号状态、organization、membership 和 billable account；不得从客户端直接接收可信 role/org/balance。
- **账本：** 余额写入、预占、结算、释放、人工调账和审计需使用数据库事务、唯一幂等约束和明确锁/并发策略。
- **AI 计量：** Translate 会并发多次调用，Generate Resume 可能重试，Chat 可能有多 step 和嵌套工具；operation 与 provider attempt 必须分层记录。
- **流式策略：** 必须明确断流、取消、供应商成功但解析失败、安全过滤和超时预占的收费/补偿规则。
- **密钥：** AI 凭据加密主密钥不得复用 `AUTH_SECRET`。优先使用 Secret Manager/KMS；若使用应用层加密，需支持版本化与轮换。
- **出站网络：** 当前模型接口允许任意 Base URL，必须在托管密钥启用前关闭。自定义 OpenAI-compatible 服务如保留，需防 SSRF 与 DNS rebinding。
- **限流：** 多实例部署需要共享限流状态。选择 Redis、托管 KV 或 PostgreSQL 前需评估一致性、延迟和依赖失败策略。
- **隐私：** usage 和审计默认只保存成本与关联元数据，不保存完整简历、JD、面试正文或 Prompt；确需保存时必须有独立保留与访问政策。
- **账号删除：** 先绘制用户数据图，区分可删除业务数据与需匿名保留的账务/安全记录；删除必须可重试且不产生半完成状态。
- **备份：** 最小备份恢复是 P0 上线条件；完整监控、告警和运维报表可进入 P1。
- **现有集成点：** 认证集中在 `src/lib/auth/`，数据集中在 `src/lib/db/`，BYOK 集中在 `src/lib/ai/provider.ts`、`src/stores/settings-store.ts` 与各 AI routes；实施时应优先建立共享服务边界，再逐路由迁移。

## 10. Success Metrics

- 生产环境中，指纹认证、SQLite 和演示 seed 的启用率为 0。
- 私有 API 认证、角色、所有权和租户矩阵自动化覆盖率为 100%；已知 IDOR 用例全部被阻止且无副作用。
- 浏览器存储、网络请求、构建产物、API 响应和日志中的 AI Key 泄漏数为 0。
- 账本并发与幂等测试中负余额、重复结算和无法核对流水数量均为 0。
- 被余额、权限、模型或限流拒绝的请求，供应商调用数和账本变动数均为 0。
- ToC 和 ToB 端到端验收各连续通过至少 3 次，刷新、退出重登后数据保持一致。
- 超管可在 5 分钟内完成单个用户调账；可在 10 分钟内完成机构开户、额度分配和管理员授权。
- 新增 Gateway 在不含供应商响应时间的情况下，对普通 AI 请求增加的服务端 P95 开销目标不超过 200ms。
- 最近一次 PostgreSQL 备份可在确认的 RTO 内恢复，恢复后的余额与流水核对差异为 0。
- `pnpm type-check`、`pnpm lint`、`pnpm test` 和 `pnpm build` 在发布候选上全部通过。
