## 1. 摘要

CareerPilot 目前是一套功能较完整的 **自托管 AI 简历编辑 / 模拟面试** 应用：具备拖拽编辑、多模板、AI 优化、导出分享、职业照与面试模拟等能力，并支持 Docker 部署与中英双语。

从「个人自用 / 演示」角度看，产品可用性较高；从「**可对外商用交付**」角度看，**尚未就绪**。核心差距集中在：

1. **缺少权限与组织体系**（无超级管理员 / 机构管理员 / 个人用户分层）；
2. **AI 能力采用用户自备 Key（BYOK）**，无法由平台统一管控成本与合规；
3. **模型与生图供给单一**，无法支撑「不同套餐 / 不同点数消耗」的商业产品；
4. **管理后台缺失**，无法同时运营 ToC 个人用户与 ToB 机构客户；
5. 另有认证强度、接口鉴权、数据合规、生产运维等需在商用前补齐的问题。

**结论建议：** 保留现有业务能力作为用户端底座，启动「商用化一期」改造。产品定位为 **ToC + ToB 双通道**：

- **ToC：** 个人用户可直接注册使用，按 **点数（Credits）** 消费 AI 能力；点数规则、发放、调账、套餐由 **超级管理员** 统一管理；
- **ToB：** 超级管理员创建机构并授权 **机构管理员**；机构侧按席位 / 机构额度运营，再服务其终端用户。

优先完成：权限体系、托管 AI、点数与套餐、管理后台，再规模化对客开通。

## 2. 商用交付目标定位

本报告按 **ToC 直接运营 + ToB 机构交付** 双模式设定，不绑定单一行业。企业、学校、培训机构等 ToB 客户共用同一套底座；个人用户走注册 + 点数通道。

### 2.1 双通道一览

| 通道 | 获客方式 | 计费 / 额度 | 谁管理 |
|------|----------|-------------|--------|
| **ToC（个人）** | 用户自行注册登录后即可使用 | **点数**：注册赠送 / 充值 / 活动发放；按模型与能力扣点 | **超级管理员** 直接管理点数规则、用户、风控 |
| **ToB（机构）** | 超管开户或商务签约后开通机构 | 机构套餐 / 席位 / 机构额度（可折算点数） | **超级管理员** 授权 **机构管理员** 管理本机构 |

> 两端共用同一用户端产品能力与同一套平台 AI 密钥；差异主要在账号归属、额度账户与管理权限。

### 2.2 目标角色模型

| 角色 | 职责 | 典型使用者 |
|------|------|------------|
| **超级管理员（Super Admin）** | 平台级：配置全局 AI 供应商与密钥、模型目录与扣点规则；管理 ToC 用户与点数（发放 / 扣减 / 冻结）；创建机构、开通套餐、任命/回收机构管理员；全局审计与风控 | 我方运营 / 技术负责人 |
| **机构管理员（Org Admin）** | ToB 客户侧：管理本机构成员与席位、查看本机构用量；在超管授权范围内调整本机构配额（可选） | 企业 HR / 学校就业办 / 培训机构运营 |
| **普通用户（End User）** | 使用简历、AI、面试等功能；**不接触 API Key**；可选择套餐允许的模型；ToC 用户消耗个人点数，ToB 用户消耗机构额度 | 个人求职者 / 员工 / 学生 / 学员 |

### 2.3 目标商业能力（一期应具备）

**共通：**

- 平台统一托管 AI（对话 / 生图），用户无感密钥；
- 模型目录 + 分档供给；调用前校验额度并扣减；
- 生产级认证、鉴权、备份与基本合规材料。

**ToC：**

- 支持个人注册 / 登录；
- 点数账户：余额查询、消费明细、不足提示；
- 超级管理员可：查用户、调账（加减点）、冻结账号、配置注册赠点与扣点单价。

**ToB：**

- 超管可开户并授权机构管理员；
- 机构管理员可管理本机构成员与用量；
- 机构额度与 ToC 点数账户隔离，避免串账。

## 3. 已识别的四项核心问题（业务侧）

以下四项为业务侧已明确提出、且经代码核对属实的关键缺口，彼此强耦合。

### 3.1 问题一：API Key 等需用户自行填写

| 项 | 说明 |
|----|------|
| **现状** | 用户在「设置 → AI 配置」中自行填写协议、API Key、地址与模型；Key 主要保存在浏览器本地，请求时由前端携带至服务端再转发模型厂商。 |
| **商用冲突** | ToC / ToB 终端用户均不应持有平台密钥；成本、限流、审计无法由平台掌控。 |
| **目标态** | 密钥仅由 **超级管理员** 在管理端维护；用户端只选择允许的模型，由服务端代理调用并扣点 / 扣机构额度。 |
| **优先级** | **P0（阻断商用）** |

### 3.2 问题二：兼容的 LLM / 图像模型过少，缺少分档供给

| 项 | 说明 |
|----|------|
| **现状** | 对话侧主要支持 OpenAI 兼容、Anthropic、Gemini；职业照等生图能力当前写死为 Gemini 图像接口。 |
| **商用冲突** | 无法形成「基础 / 进阶 / 旗舰」差异；无法按模型设置不同扣点数；扩展 gpt-image、文心图像等需改造架构。 |
| **目标态** | 管理端维护模型目录（对话 + 生图）及 **单次/千 Token 扣点规则**；套餐或用户等级绑定可用模型集合。 |
| **优先级** | **P1（商业闭环必需）**，架构预留应在 P0 同步设计 |

### 3.3 问题三：界面观感偏「AI 模板化」

| 项 | 说明 |
|----|------|
| **现状** | 通用落地页与组件库风格，品牌切换能力有限，缺少面向正式产品与机构白标的信息架构。 |
| **商用冲突** | 影响 ToC 转化与 ToB 招采观感。 |
| **目标态** | 强化注册 / 点数 / 套餐等商业入口；机构可配置品牌；弱化通用 AI 工具感。 |
| **优先级** | **P2（体验与品牌）**，可与 P0/P1 并行启动设计 |

### 3.4 问题四：未划分用户端与管理员端；AI 配置应在管理侧

| 项 | 说明 |
|----|------|
| **现状** | 用户模型扁平，无角色字段；无管理后台；无套餐 / 点数；所有登录用户功能面基本一致。 |
| **商用冲突** | 无法实现超管运营 ToC 点数、无法授权 ToB 机构管理员。 |
| **目标态** | 独立管理端 + 用户端；超管直管 ToC；超管授权机构管理员管 ToB。 |
| **优先级** | **P0（阻断商用）** |

**耦合关系：** 无管理端 → 密钥只能用户自填 → 无法做点数 / 套餐 → ToC 与 ToB 商业模式均无法落地。

## 4. 技术与产品深入审计（补充问题）

### 4.1 问题汇总表

| 编号 | 领域 | 级别 | 发现 | 商用影响 | 建议 |
|------|------|------|------|----------|------|
| A1 | 认证 | P0 | 默认浏览器指纹登录，客户端可伪造身份头 | 多用户与 ToC 注册体系下冒用风险高 | 生产关闭指纹；ToC 用邮箱/手机/OAuth 注册登录 |
| A2 | 安全 | P0 | 部分 AI / 会话 / 生图 / 模型列表接口鉴权或归属不足 | 越权、刷点、开放代理滥用 | 全量鉴权 + 所有权校验 + 限流 |
| A3 | 账号体系 | P0 | 无标准注册体系、无点数账户、无机构模型 | 无法同时支撑 ToC 与 ToB | 用户注册 + 点数账本 + 机构/成员/角色 |
| A4 | 计费配额 | P0/P1 | 无套餐、点数、席位、用量计量、支付 | 无法对 C 扣点、对 B 控额 | 先做点数账本与套餐；支付可二期接入 |
| A5 | 隐私合规 | P0 | 缺账号注销/全量导出；隐私政策入口不完整 | ToC 上架与 ToB 招采风险 | 注销级联、导出、正式隐私政策与用户协议 |
| A6 | 分享安全 | P1 | 分享密码哈希强度不足 | 公开链接被破解风险 | 强化哈希；避免明文出现在查询串 |
| A7 | 数据库运维 | P0 | 默认 SQLite 不适合多用户；双库 schema 有漂移风险 | ToC 并发与数据完整性风险 | 商用强制 PostgreSQL；统一迁移 |
| A8 | 运维可观测 | P1 | 缺健康检查、备份与监控规范 | 交付后运维成本高 | `/health`、备份、告警 |
| A9 | 运营能力 | P1 | 缺超管运营台（用户、调账、风控）与机构报表 | 无法日常运营 ToC/ToB | 超管后台 + 机构报表 |
| A10 | 工程债 | P1 | 认证库 beta、测试偏少、CI 偏镜像发布 | 质量与安全回归不足 | 稳定认证 + 鉴权/扣点测试门禁 |
| A11 | 法务 | P1 | 可商用但需完善开源归属与对外声明 | 对外销售材料不完整 | NOTICE 与修改声明 |

### 4.2 现有可复用优势

- 简历编辑、模板、导出、分享、面试模拟等业务闭环较完整；
- 中英国际化已具备；
- Docker 交付路径清晰，具备 PostgreSQL 切换条件；
- 多数简历读写接口已有用户归属校验；
- AI Key 当前未作为长期机密写入服务端用户配置，有利于迁移到平台托管 Key + 点数扣减模式。

## 5. 建议的目标架构（商用一期）

### 5.1 权限与双通道组织

```
超级管理员（平台）
    ├── 全局：AI 供应商密钥、模型目录、扣点规则、风控策略
    ├── ToC：个人用户管理、点数发放/调账/冻结、注册赠点配置
    ├── ToB：创建机构、开通套餐、任命/回收机构管理员
    └── 全局审计与报表
         │
         ├────────────── ToC ──────────────┐
         │                                 ▼
         │                    个人用户（自行注册）
         │                    · 个人点数账户
         │                    · 选模型、耗点用 AI
         │                    · 不接触 API Key
         │
         └────────────── ToB ──────────────┐
                                           ▼
                              机构管理员（超管授权）
                              · 本机构成员与席位
                              · 本机构额度 / 报表
                                           │
                                           ▼
                              机构内终端用户
                              · 使用业务功能
                              · 消耗机构额度
                              · 不接触 API Key
```

### 5.2 AI 调用与点数扣减（目标）

**现状：** 用户浏览器持有 Key → 请求头传给应用服务 → 转发厂商。  

**目标：**

1. 超级管理员配置平台密钥与模型扣点规则；  
2. 用户发起 AI 请求并选择模型；  
3. 服务端判定账户类型（个人点数 / 机构额度）→ 校验余额 → 代理调用 → 成功后扣减并记账；  
4. 余额不足时拒绝调用并引导充值（ToC）或联系管理员（ToB）。

### 5.3 点数与套餐（示意）

**ToC 点数示例：**

| 能力类型 | 示意扣点 | 说明 |
|----------|----------|------|
| 基础对话模型 | 1 点 / 次或按 Token 折算 | 注册可赠送起始点数 |
| 进阶 / 旗舰对话 | 3–10 点 | 由超管在模型目录配置 |
| 标准生图 | 10 点 / 张 | 含职业照等 |
| 高阶生图 | 20 点 / 张 | 多厂商旗舰模型 |

**ToB 套餐示例：**

| 档位 | 对话 | 生图 | 额度逻辑 |
|------|------|------|----------|
| 基础版 | 性价比模型 | 可选 | 机构月额度或席位数 |
| 专业版 | 更强模型 | 标准生图 | 更高额度 |
| 旗舰版 | 旗舰模型 | 多厂商生图 | 最高额度 / 专属配置 |

点数单价、赠送策略、机构套餐均由 **超级管理员** 配置；机构管理员不掌握平台密钥。

### 5.4 超级管理员对 ToC 的直接管理范围（一期）

- 用户列表：查询、禁用 / 解禁；  
- 点数：发放、扣减、调账备注、流水查询；  
- 规则：注册赠点、各模型扣点、每日上限；  
- 风控：异常刷点监测、手动冻结；  
- （二期）充值商品、支付对账、活动批次发点。

## 6. 分期实施建议

### 6.1 一期（P0）：可安全对客的双通道底座

**建议周期：** 约 2–4 周（视人力而定）

1. 角色模型：超级管理员、机构管理员、普通用户；  
2. ToC：注册 / 登录、个人点数账户、消费流水；  
3. 管理后台（超管）：AI 密钥与模型目录、扣点规则、ToC 用户与调账、机构开通与管理员授权；  
4. 用户端取消自填 Key；服务端托管调用 + 扣点 / 扣机构额度；  
5. 关闭生产指纹登录；强化 API 鉴权与归属校验；  
6. 商用强制 PostgreSQL；账号注销与用户协议 / 隐私政策。

**一期验收标准（建议）：**

- 个人用户可注册并靠点数使用 AI（不可见 Key）；  
- 超管可对个人用户加减点并查看流水；  
- 超管可创建机构并任命机构管理员；  
- 核心 API 具备登录态、归属校验与余额校验；  
- 生产配置检查清单通过。

### 6.2 二期（P1）：可售卖与可运营

**建议周期：** 约 4–8 周

1. ToC 充值 / 套餐包（可先对接一种支付）；  
2. 多厂商对话与生图扩展；完善分档模型；  
3. 机构报表、审计日志、成员管理完善；  
4. 备份监控、健康检查与运维文档；  
5. 超管运营报表（耗点排行、成本估算）。

### 6.3 三期（P2）：体验与规模化

1. UI 去模板化、ToC 增长转化优化、机构白标；  
2. 更多支付渠道与发票能力；  
3. 无障碍与招采材料；  
4. 按客户类型叠加行业模块。

## 7. 风险与依赖

| 风险 | 说明 | 缓解 |
|------|------|------|
| 模型成本不可控 | 托管 Key 后费用由平台承担（ToC）或需向机构结算（ToB） | 硬配额、扣点、告警、成本看板 |
| ToC 刷点 / 滥用 | 注册羊毛、脚本刷接口 | 验证码、限流、设备/风控、异常调账 |
| 账务一致性 | 调用成功但扣点失败等 | 事务或出账补偿；以流水为准可审计 |
| 认证对接 | 政企 / 校园可能需 SSO | 一期预留 OIDC；二期对接 |
| 开源合规 | 需保留许可证与归属说明 | 法务复核 NOTICE 与对外声明 |
| 范围蔓延 | ToC 支付、UI、多行业同时开工易延期 | 严格按 P0→P1→P2；一期先支持「超管手工发点」也可上线内测 |

## 8. 结论与请示事项

### 8.1 结论

1. **现版本适合作为用户端业务底座，不适合直接作为商用版本对外售卖或规模化开通。**  
2. 业务侧四项问题成立；商用需同时支持 **ToC（注册 + 点数，超管直管）** 与 **ToB（超管授权机构管理员）**。  
3. 建议一期先打通：权限、托管 AI、点数账本、超管后台；支付与精致化体验放到二期及以后。

### 8.2 提请部门决策

请部门审阅并明确：

1. **是否立项启动商用化一期（P0）改造；**  
2. **一期是否双通道同时上线**（建议：ToC 注册+点数 与 ToB 机构开户同期具备，支付可后置，超管先手工发点 / 开通）；  
3. **ToC 点数策略倾向**：仅注册赠点内测，还是一期就接充值支付；  
4. **ToB 计费倾向**：机构年费包额度、按席位，或机构点数包；  
5. **是否由本团队立即开展管理端 + 托管 AI + 点数账本的详细设计与排期。**
