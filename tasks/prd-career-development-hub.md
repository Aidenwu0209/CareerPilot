# PRD: CareerPilot 职业发展中心（校赛闭环版）

| 项目 | 内容 |
|---|---|
| 文档状态 | 已按用户确认的推荐方案进入实施 |
| 产品目标 | 在现有简历、JD 分析和模拟面试之上，形成学生职业画像、目标、匹配、路径、成长与教师指导闭环 |
| 首批范围 | 人工审核的典型岗位知识；学生职业驾驶舱；教师学生列表、详情、点评与成长任务 |
| 技术路线 | 保留 Next.js 16 + Drizzle 主系统；岗位图谱与 RAG 采用可插拔 Provider，不恢复旧 FastAPI 双栈 |

## 1. Introduction

CareerPilot 当前的核心入口是简历列表，职业数据分散在简历模块、JD 分析和面试报告中。职业发展中心把这些材料转换成可追溯的能力证据，形成版本化职业画像，并根据目标岗位生成可解释匹配结果和成长任务。教师在机构授权范围内查看学生、确认材料、给出指导并分派任务；学生完成任务后生成新的能力快照，从而完成“规划 -> 执行 -> 反馈 -> 再规划”。

## 2. Goals

- 学生能在一个驾驶舱中看清目标岗位、画像完整度、岗位匹配、能力差距、成长路径和下一步行动。
- 每一项能力和匹配判断都能追溯到简历、项目、证书、JD、面试报告或教师确认等证据。
- 学生能设置一个主目标和最多两个备选目标，并保留目标变更历史。
- 首批岗位知识覆盖人工审核的典型岗位，包含技能要求、能力要求、晋升/转岗关系和来源信息。
- 教师只能访问自己机构且被分配的学生，并能提交公开指导、私有备注和成长任务。
- 学生成长任务完成后产生新的画像快照，界面能解释能力变化的来源。
- RAG 只负责检索、解释和引用；结构化匹配分不由自由生成文本直接决定。

## 3. Confirmed Assumptions

1. 第一版以校赛可演示的真实闭环为目标，不做全行业生产规模。
2. 首批岗位采用仓库内人工审核数据，不在运行时抓取招聘网站。
3. 教师端第一版包含学生列表、学生详情、点评、证据确认和任务闭环。
4. 当前 Next.js/Drizzle 应用是唯一业务与认证主系统。
5. PostgreSQL 是生产基线，SQLite 继续作为本地开发适配器；新增表必须保持两套 schema 语义一致。
6. 当前机构商业角色不直接改成教育角色；教师、学生等教育角色通过独立分配表表达。

## 4. Delivery Order

| 波次 | Stories | 退出条件 |
|---|---|---|
| W0 数据与权限 | US-001、US-002、US-008 | schema、种子、租户和教师学生授权通过测试 |
| W1 学生闭环 | US-003 - US-007 | 学生能从目标选择走到匹配、路径和成长任务 |
| W2 教师闭环 | US-009 - US-011 | 教师能处理待办、指导学生并触发可解释变化 |
| W3 集成验收 | US-012 | 端到端闭环、类型检查、测试、构建和浏览器验证通过 |

## 5. User Stories

### US-001: 职业发展领域数据基线

**描述：** 作为平台开发者，我需要持久化职业画像、证据、目标、岗位知识、匹配、路径和成长任务，以便刷新和重启后仍能回溯完整职业发展过程。

**Acceptance Criteria：**

- [ ] SQLite 与 PostgreSQL schema 均包含职业画像快照、画像证据、职业目标、岗位、岗位要求、岗位关系、匹配运行、成长任务和教师指导所需实体。
- [ ] 新增实体包含租户或用户归属、创建时间和必要索引；学生数据不能因仅知道 ID 被其他用户读取。
- [ ] 全新本地数据库执行迁移和 seed 后出现至少 10 个来源明确的典型岗位。
- [ ] 重复执行 seed 不产生重复岗位、要求或岗位关系。
- [ ] `pnpm type-check`、schema 测试和迁移状态测试通过。

### US-002: 教育角色与教师学生授权

**描述：** 作为学校机构管理员，我希望在现有机构成员关系上分配教师、学生及指导关系，以便教师只能处理获授权的学生。

**Acceptance Criteria：**

- [ ] 一个机构成员可拥有学生、教师或职业指导教师教育角色，且不影响现有 `org_admin/member` 商业角色。
- [ ] 教师学生关系同时受机构、有效 membership 和有效指导分配约束。
- [ ] 教师访问未分配学生、其他机构学生或已移除学生时返回不泄漏目标信息的 `403/404`。
- [ ] 学生不能读取教师私有备注，普通机构成员不能访问教师工作台 API。
- [ ] 跨机构、未分配、已停用机构和已移除 membership 场景均有自动化测试。

### US-003: 从现有材料生成可追溯职业画像

**描述：** 作为学生，我希望系统利用现有简历、JD 分析和面试报告形成职业画像，以便不必重复录入已有材料。

**Acceptance Criteria：**

- [ ] 画像至少展示专业基础、职业技能、项目实践、通用能力、求职准备和发展潜力六个维度。
- [ ] 每个能力项显示当前等级、证据数量、证据来源和最后更新时间。
- [ ] 缺失材料显示“证据不足”，不能静默按零分处理。
- [ ] 重新生成画像时创建新快照，不覆盖旧快照。
- [ ] 查看某个能力项时只能看到当前用户拥有的简历、面试或教师公开证据。

### US-004: 设置和版本化职业目标

**描述：** 作为学生，我希望设置主目标岗位和备选岗位，以便匹配、路径和成长计划围绕明确方向生成。

**Acceptance Criteria：**

- [ ] 学生可选择一个主目标和最多两个备选岗位，并填写目标时间和偏好。
- [ ] 更改主目标需要确认，保存后驾驶舱、匹配和成长路径立即使用新目标。
- [ ] 刷新页面后目标保持，旧目标在历史记录中可见。
- [ ] 无目标时显示明确空状态和“选择目标岗位”主操作。
- [ ] 使用浏览器打开 `/zh/career/goals`，选择并保存岗位后返回 `/zh/career`，首屏显示相同目标且控制台无错误。

### US-005: 可解释人岗匹配

**描述：** 作为学生，我希望了解自己与目标岗位在哪些方面匹配、哪些方面缺少证据，以便制定可信行动计划。

**Acceptance Criteria：**

- [ ] 匹配结果分别显示硬性要求、技能覆盖、实践证据、通用能力和偏好约束，不只显示单一总分。
- [ ] 页面独立显示匹配分、证据覆盖率和结果置信度。
- [ ] 每个匹配项显示岗位要求、学生证据、差距及建议；未知信息标记为“待补充”。
- [ ] 同一画像快照、岗位版本和规则版本重复计算得到相同结构化得分。
- [ ] 使用浏览器打开 `/zh/career/matching`，展开一个差距项后能看到来源与行动建议，且控制台无错误。

### US-006: 职业路径和成长任务

**描述：** 作为学生，我希望把岗位差距转换成阶段和任务，以便知道本周而不是只知道长期应该做什么。

**Acceptance Criteria：**

- [ ] 路径至少包含当前准备阶段、目标岗位阶段和一个可选后续/转岗阶段。
- [ ] 系统根据差距生成短期、中期任务，任务包含原因、截止时间、关联能力和完成标准。
- [ ] 学生可以开始、完成任务并填写成果说明；刷新后状态保持。
- [ ] 完成任务不会直接提高能力分，只有提交并确认的新证据才能生成新的能力快照。
- [ ] 使用浏览器打开 `/zh/career/path`，完成一个任务后页面显示已完成状态和待确认证据状态，且控制台无错误。

### US-007: 岗位知识、职业图谱与可引用检索

**描述：** 作为学生，我希望查看岗位要求、关系和有来源的解释，以便理解推荐依据而不是接受黑盒结论。

**Acceptance Criteria：**

- [ ] 岗位详情包含摘要、技能/能力要求、相关证书、来源和版本时间。
- [ ] 岗位要求由结构化要求表表达；岗位关系至少支持 `progresses_to`、`transfers_to` 和 `related_to`。
- [ ] 职业路径查询通过 Provider 接口完成；默认实现可使用关系表，未来可替换图数据库。
- [ ] 知识检索结果返回标题、来源、引用片段和相关度；无知识命中时明确说明资料不足。
- [ ] RAG 解释引用知识来源，但不得修改结构化匹配分。
- [ ] 使用浏览器打开 `/zh/career/jobs`，进入岗位详情后能看到要求、关系和至少一个来源，且控制台无错误。

### US-008: 学生职业驾驶舱

**描述：** 作为学生，我希望进入职业发展中心就看到目标、现状、差距、路径和下一步，以便快速做出行动决策。

**Acceptance Criteria：**

- [ ] `/zh/career` 首屏显示主目标、画像完整度、匹配分、证据覆盖率和下一里程碑。
- [ ] 页面展示六维能力、近期能力变化、成长路径、本周任务和教师最新公开指导。
- [ ] 每张卡片都提供进入画像、目标、匹配、路径或岗位知识的明确入口。
- [ ] 桌面 1280px 和移动 390px 下无横向溢出，中文标题不出现单字孤行。
- [ ] 使用浏览器从全局导航进入 `/zh/career`，能够继续到目标、匹配和路径页面，且控制台无错误。

### US-009: 教师待办与学生列表

**描述：** 作为教师，我希望首先看到需要我处理的学生和原因，以便把时间用在可行动的指导上。

**Acceptance Criteria：**

- [ ] `/zh/teacher` 显示待确认材料、目标变更、逾期任务、匹配下降和近期进步等队列摘要。
- [ ] 学生列表支持按状态和目标岗位筛选，并显示当前目标、匹配分、任务进度和最近变化。
- [ ] 教师只能看到有效分配的本机构学生。
- [ ] 无分配学生、无待办、无权限和请求失败均有明确页面状态。
- [ ] 使用教师账号打开 `/zh/teacher`，筛选“需要关注”后列表只显示对应学生，且控制台无错误。

### US-010: 教师查看学生与提交指导

**描述：** 作为教师，我希望在一个学生详情页查看画像、证据、目标、路径和任务，并留下可控制可见性的指导。

**Acceptance Criteria：**

- [ ] 学生详情包含概览、画像与证据、目标与路径、成长任务、指导记录五个区域。
- [ ] 教师可提交“学生可见指导”或“教师私有备注”；保存后立即出现在对应记录中，刷新后保持。
- [ ] 学生页面只能看到学生可见指导，私有备注不出现在学生 API 响应中。
- [ ] 教师能为学生创建关联能力和截止时间的成长任务，学生驾驶舱随即显示该任务。
- [ ] 使用浏览器在 `/zh/teacher/students/[id]` 提交公开指导和任务，再以学生视角打开 `/zh/career`，两项内容均出现且控制台无错误。

### US-011: 证据确认与能力变化解释

**描述：** 作为教师和学生，我希望能力变化能说明由什么证据引起，以便分数可信且可以复核。

**Acceptance Criteria：**

- [ ] 学生提交任务成果后生成待确认画像证据，不直接更改当前能力分。
- [ ] 教师确认或退回证据时必须填写理由；结果对学生可见。
- [ ] 确认证据后生成新画像快照，并记录旧值、新值、变化量和关联证据。
- [ ] 能力变化时间线支持按能力查看，不把材料新增时间误作能力提升时间。
- [ ] 使用浏览器确认一条证据后，学生 `/zh/career/profile` 显示对应变化和来源，刷新后保持。

### US-012: 职业发展闭环集成验收

**描述：** 作为产品负责人，我希望用真实运行路径证明学生和教师功能已经连通，而不是只存在静态页面。

**Acceptance Criteria：**

- [ ] 演示学生完成“进入驾驶舱 -> 选择目标 -> 查看匹配 -> 接收成长任务 -> 提交成果”的完整流程。
- [ ] 演示教师完成“进入待办 -> 打开学生 -> 查看证据 -> 提交指导/任务 -> 确认证据”的完整流程。
- [ ] 回到学生端后能看到教师指导、任务状态和可解释能力变化。
- [ ] 未授权教师访问目标学生详情被拒绝，且目标是否存在不被泄漏。
- [ ] `pnpm type-check`、`pnpm lint`、`pnpm test` 和 `pnpm build` 通过。
- [ ] 使用浏览器在 1280x720 和 390x844 完成关键页面验收，控制台无新增错误。

## 6. Functional Requirements

- FR-1: 系统必须以版本化快照保存职业画像和能力变化。
- FR-2: 系统必须把原始事实、AI 推断、教师意见和学生自述标记为不同证据类型。
- FR-3: 系统必须支持一个主目标和最多两个备选岗位。
- FR-4: 匹配引擎必须分离结构化评分、证据覆盖率和置信度。
- FR-5: 成长任务必须关联目标、能力、原因、截止时间和完成证据。
- FR-6: 岗位知识必须保留来源和版本，图谱查询必须经 Provider 边界。
- FR-7: 教师数据访问必须同时满足平台认证、机构有效、教育角色有效和指导分配有效。
- FR-8: 学生接口不得返回教师私有备注。
- FR-9: 所有新 UI 必须支持中文、英文、深色模式和移动端重排。
- FR-10: 新增数据必须纳入账号导出和删除边界检查。

## 7. Non-Goals

- 不在第一版实时抓取招聘网站或声称覆盖全行业岗位。
- 不在第一版部署 Neo4j、RAGFlow 或复杂多智能体作为硬依赖。
- 不做未验证的心理测评、人格诊断或就业结果承诺。
- 不让 LLM 自由生成不可复现的最终匹配分。
- 不做学院级大屏、就业率预测和跨校数据对比。
- 不允许教师默认查看本机构全部学生的简历或面试全文。

## 8. Design Considerations

- 学生驾驶舱首先回答“目标、现状、差距、下一步”，避免堆积统计卡。
- 能力图同时提供文字和数值，不只依赖雷达图或颜色。
- 教师首页以工作队列为主，以聚合统计为辅。
- 岗位匹配详情按“要求 -> 学生证据 -> 差距 -> 行动”展示。
- 复用现有 Header、Button、Card、Badge、Progress、Dialog、Sheet 和暗色模式设计语言。

## 9. Technical Considerations

- 页面默认使用 Server Components 读取数据库；交互表单和筛选下沉到小型 Client Components。
- Route Handlers 默认动态执行，并在服务层完成所有权和租户校验。
- 当前远端 `main` 已包含 `develop/careerpilot`；实现直接基于 `main`。
- 生产 schema 以 PostgreSQL 文件和迁移为基线，SQLite schema 用于本地兼容测试。
- 初版岗位图谱可用关系表和 BFS/邻接查询；Provider 接口为以后接入图数据库留边界。
- 初版检索可使用本地确定性文本检索；Provider 接口返回带来源的统一结果，之后可替换向量检索或 RAG 服务。

## 10. Success Metrics

- 演示学生在 3 分钟内完成从选择目标到获得成长任务。
- 所有匹配维度都有要求、证据或“待补充”状态，不出现无来源分数。
- 教师从待办队列进入目标学生并创建任务不超过 3 次主要点击。
- 100% 教师学生详情请求经过机构和指导分配校验。
- 关键学生与教师闭环有自动化测试和浏览器证据。

## 11. Open Questions

- 首批典型岗位最终由哪个专业或比赛演示场景确定？默认先覆盖计算机、产品、数据和运营方向。
- 教师确认能力证据后是否允许修改分值，还是只确认系统建议？第一版默认只确认或退回系统建议。
- 生产 RAG 供应商和向量存储尚未确定，第一版通过 Provider 隔离。
